STAGE 0The bug & the spec

One message the spec forbids

Bug CU07. ARCANE's own one-line description, verbatim: "gNB-CU crashes when receiving F1AP Setup Response" (test_runner.py:633). In plain English: the gNB-CU is the brain of the cell tower — it runs one program (nr-softmodem) that every connected phone depends on. Its helper below it (the gNB-DU) is supposed to say hello first, with an F1-Setup-Request, and only then does the brain reply with an F1-Setup-Response. The bug is what happens when someone skips the hello and just sends the Response out of nowhere: instead of ignoring it — or replying with an error, which is what a well-built program would do — the CU's entire process crashes (SIGSEGV, exit code 139). One uninvited message. No hack, no malformed data — just a reply that arrived without its question. The whole tower goes down, and every phone it was serving loses the network until someone restarts it.

That is what makes it a real bug and not a rough edge. The message itself is perfect — 68 bytes re-encoded from a genuine capture, decoding cleanly as F1-Setup-Response · gNB-Eurecom-CU · RRC 17.3.0 — so nothing about its content is at fault. Only its timing is wrong: it arrives first, with no Request ever sent, something the spec (§8.2.3, §9.2.1.5 below) says cannot happen. A crashed process is the worst possible answer to a message like that.

The purpose of the F1 Setup procedure is to exchange application level data needed for the
gNB-DU and the gNB-CU to correctly interoperate on the F1 interface. This procedure shall be
the first F1AP procedure triggered for the F1-C interface instance after a TNL association has
become operational.

        — ETSI TS 138 473 V16.13.0, §8.2.3.1 (p. 25)
This message is sent by the gNB-CU to transfer information associated to an F1-C interface instance.

       Direction: gNB-CU → gNB-DU

        — ETSI TS 138 473 V16.13.0, §9.2.1.5 (p. 93)

The Response may therefore only ever flow CU → DU. Arriving from a DU with no Request
outstanding, it cannot exist in an honest session — a compliant CU discards it.
8.2.3.4   Abnormal Conditions

Not applicable.

        — ETSI TS 138 473 V16.13.0, §8.2.3.4 (p. 28)

The spec defines no recovery behaviour for a broken F1 Setup exchange — implementations
get no guidance here, which is exactly where fuzzers hunt.
-- TS 38.473 v16.3.1 (the ASN.1 the target CU was compiled against)
f1Setup F1AP-ELEMENTARY-PROCEDURE ::= {
    INITIATING MESSAGE       F1SetupRequest      -- DU → CU
    SUCCESSFUL OUTCOME       F1SetupResponse     -- CU → DU
    UNSUCCESSFUL OUTCOME     F1SetupFailure      -- CU → DU
    PROCEDURE CODE           id-F1Setup
    CRITICALITY              reject
}

Why this stage matters: ARCANE's published seed model carries no
    direction information — the gap that makes an unsolicited Response look walkable. All three
    framings here preserved it. Framing B went further and modeled the attack itself as an edge
    with expected_result: reject — OAI's real answer is SIGSEGV.
    

Recorded limitation: GLM is a reasoning model; pass 1 burned its 32 768-token
    output on thinking and truncated the JSON. Pass 2 added a compactness clause. That
    unreliability is part of the honest story.

STAGE 3Test cases & elimination

    
How 16 paths become one attack

    
State space explodes; the funnel keeps it testable. Every pruning stage is
    seeded and logged (seed 20260828) — this is the answer to
    "how do you eliminate test cases?"

    

    
The seam worth knowing: ARCANE's shipped run used max_paths=10 —
    with that cap the DFS never reaches any response branch (their own 100 emitted cases contain
    zero). Raising the cap to 200 is what exposes the CU07 path. Framing B scored 0 here because
    B's model already contains the attack as an explicit edge — it needs no mutation to find it.
